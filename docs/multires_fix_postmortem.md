# 多分辨率图像与伴音故障修复复盘

2026-10-06，分支 `fix/multires-engine-timing`。本文记录从稳定的 720p 版本到多分辨率上板验证通过的排查链。原始抓包和卡镜像保存在本机被 Git 忽略的 `img/golden/`、`img/*.img`，下表保留关键数字与散列，便于复核。

## 最终结论与验证边界

- 用户确认 HDMI 与 PC 读回预览中的大面积白条、图像撕裂已消失，1280×720、571×720（IMG4）、640×480（IMG5）均可正常显示。此前 IMG5 配对 WAV 的杂音在写口越界修复后由用户报告为“基本消失”；本轮没有做新的模拟音频频谱测量。
- 最终源码在 100 MHz `sd_card_clk`、100 MHz `ext_mem_clk` 下运行。整帧填黑源每 **16 拍送一个 32 位零字**；图像会话的左右黑色 padding 每 **4 拍送一个像素**，即每 **8 拍组成一个 32 位字**。图像窗口内的像素继续按原逻辑、由 SD/BMP 数据与 64 像素缓冲驱动。
- 最终真实板抓包：IMG4 写侧 460800/460800 字吻合 BMP，读回 153600/153600 个抽样字全帧吻合；IMG5 写侧 307200/307200 字吻合 BMP，第二次装载读回 153600/153600 个抽样字全帧吻合。IMG5 首次装载曾在下黑边出现 1 个非白色单字差异，见下表。
- 读回探针每 **3 个 32 位显存字抽 1 个**，覆盖约 33% 的显存字；这些结果是抽样比较，不能宣称对未抽样的全部物理像素都做过逐点验证。用户的 HDMI 目视结果与 PC 预览一致。
- 最终 bit 的 SHA-256 为 `2f0557023ea22cf437c59dfd20dd0cb532eefeae561c121ab374effc97b31ebf`，生成于 2026-10-06 03:03:56。本 bit 对应最终限速源码；Git 中被跟踪的 TD bit、报告随全量提交保存。

## 架构、颜色与探针的真实范围

```text
TF 卡 BMP → FAT32/bmp_dec → 像素缓冲 → img_word ─────────→ 探针 A（type 3）
                                      │
整帧填黑零字 ─────────────────────────┴→ 写数据 mux → 写异步 FIFO → App 写口
配对 WAV 32 位字 ──────────────────────┘                         │
                                                         SDRAM 控制器/IP 与存储阵列
                                                                  │
                                            Sdr_rd_en/dout → 探针 B（type 4，3:1）
                                                                  │
                                                  读异步 FIFO → video_delay → HDMI
```

`DUMP_WRITE_PORT=0` 时，探针 A 接 `sd_card_bmp.tap_word=img_word`、`tap_val=img_word_val`，在写数据 mux **之前**，只覆盖图像会话；它不观察前置的整帧填黑会话。网页写侧 canvas 先创建全黑背景，图像高度以外的黑边是浏览器默认值，不能当作 SDRAM 已写零的证据。图像会话每行仍发满 1280 像素：窗口外 `px_src=0`，所以**左右**黑色 padding 的零字会经过 A；IMG5 的**上下**黑边只靠前置填黑会话，A 看不到。

探针 B 在 `DUMP_AT_SDRAM_OUTPUT=1`、`DUMP_READ_REQUEST_ADDR=0` 时取 `Sdr_rd_en/Sdr_rd_dout`，位置在视频读 FIFO 前。网页按 `display_word_index=3*j` 绘制第 `j` 个抽样字；完整帧须同时满足 153600 字、`X-Frame-Gaps=0`，并与所选 BMP 的目录项匹配。RGB565 黑像素为 `0x0000`，白像素为 `0xFFFF`，两个白像素打包为 `0xFFFFFFFF`；白字并不意味着零的每一位发生了翻转。

`scripts/analyze_frame_dump.py` 现在同时报告 `image_sample_words/read_exact_at_address` 和 `border_sample_words/border_exact_black`、`full_sample_words/full_exact_at_address`。最初只看图像窗口，使 IMG5 的大片上下白边没有进入统计，曾严重低估故障；网页 BMP 对照也已补上全帧黑边比较。

## 排查时间线：证据、误判与撤回

1. **初始症状与分辨率**：IMG2、IMG4 可辨认原图却出现大量小长方条和模糊；伴音可听出旋律但有杂音。建立以太网图像预览与读回抽样通道，BMP 必须与当前目录项逐一对应，不能把 IMG2 与 IMG4 的截图混比。
2. **先试时钟，未解决**：SDRAM 从 125 MHz 降至 100 MHz，重设移相时钟。图像和音频问题基本未变，仅错位数值变化。旧版 125 MHz 的 bit、PLL、报告保存在 `img/golden/clock125/`。因此负的 SDRAM DQ WNS 是既存风险，不足以解释本轮新增症状；频率试验没有给出修复。
3. **写侧、读侧与地址分段**：图像发射探针 A 与原 BMP 逐字对上；B 在 SDRAM 返回口出现位移。曾临时把探针切到 `App_wr_din/addr` 和 `App_rd_addr`：IMG1 全量 App 写数据 460800/460800、抽样写地址与读请求地址均正确。IMG4 的密集写口探针自身会溢出，不能把其不完整帧当成板上坏写的证据。
4. **第一个确定的 RTL 错误**：真实官方写 FIFO 的 `boardtest framepath` 重现 `App_wr_en` 末尾多一拍：请求长度 1024，却发 1025 次、末地址 1024。写引擎计数比较未计入当前在途 `App_wr_en`。`96b6608` 修正后仿真精确为 1024 次；板上音频杂音基本消失、画面大幅改善，但 IMG4 仍固定偏移 2 字。
5. **图像首字与 FIFO 清零**：窄图行首黑色可立即高速发射，在写会话 ACK 当拍 FIFO 仍处异步清零。图像会话在 ACK 后等待 16 个 SD 时钟再启动 `img_emit_en`。上板后 IMG4 的全局 `+2` 字位移消失；IMG1、IMG2 的全宽图读回基本正确。
6. **承认探针覆盖遗漏**：最初 Python/网页比较只统计图像窗口内的抽样字，错误地把“只剩几十个坏字”描述为整幅画面的状态。用户截图中黑边多条白点横线；独立按原始 B 二进制复原 PC canvas 后与截图吻合。全帧比较发现限速前 IMG5 黑边 29292/102400 个抽样字非黑，而图像内部已全对。A 的上下黑边是默认 canvas，不是填黑数据探针。
7. **读写仲裁竞态**：对比 `09ec7c6` 与稳定框架，`into_burst` 被寄存后，使用拍未复查当前读忙。最小 Verilator 用例在旧 RTL 得到 `App_rd_busy=1` 且写侧进入 `S_WRITE_BURST`；加 `into_burst_r && ~App_rd_busy` 后通过。此项让图像本体稳定，但未消除黑边。
8. **被推翻的填黑等待假设**：尝试让填黑也在 ACK 后等 16 拍，板上白边基本不变；随即撤回。该轮物理实现约 15 分 59 秒，其中布线 12 分 14 秒，逻辑综合约 4 分钟。布线耗时不随新增 RTL 行数线性变化，不能用编译变慢推断逻辑是否正确。
   同期发现 PLL 已改 100 MHz，而 `global_def.v` 刷新周期仍按 125 MHz 写。曾在假设性的刷新模型中试过读写使能门控，但没有真实 IP 的接受条件证据，也无法解释全黑突发的分布，因此**未把该实验交给板上验证并撤回源码**。刷新宏不一致作为独立遗留项保留，不能将模型实验当成已经确认的根因。
9. **前置整帧填黑限速**：新填黑源原来 `write_en=1`，100 MHz 每拍提供一个零字；旧图像像素由 25 MHz SPI 字节流间接供给，平均速率低得多。填黑改为每 16 拍一字后，IMG5 黑边错误从 **29292 降到 499**，重复装载在 **165–416** 之间；IMG4 从 **1245 降到 747**。IMG5 的上下纯填黑区从大片白条变为至多一个零星字，残差主要在图像每行左右侧边。
10. **被推翻的“跨行写突发”假设**：256 字突发编号 `% 5 == 2` 恰好跨越 640 字行尾，最初所有完整残留白段都落在这类突发。改为 128 字写突发后，IMG5 黑边错误反而从约 **499 增至 9274**，且只在每行第 0、4 个全黑的 128 字突发；图像内部仍全对。由此修正解释：先前的 `% 5 == 2` 同时是**完整的全黑突发**，不能仅凭同一索引把跨行认作根因。128 字改动已撤回，读写突发保持 256 字。
11. **限速图像左右 padding，视觉故障消失**：`in_h=0` 时 `px_src=0`，原发射块每拍推进一个黑像素、约每 2 拍组成一个字；现在仅黑色 padding 每 4 拍推进一个像素，约每 8 拍组成一个字。彩色窗口仍由 `!ibuf_empty` 控制，不改变像素序。实际 SPI 时序下，333×217 与 640×480 临时窄图卡的多次装载均与 golden 逐像素一致。最终板上用户确认黑边白条消失。

## 为什么两处限速有效，以及尚不能证明什么

| 数据源 | 修改前最高发射节奏 | 最终节奏 | 作用范围 |
|---|---:|---:|---|
| 整帧填黑 | 100 MHz，每拍一个 32 位零字 | 6.25 M 字/秒，每 16 拍一字 | 全帧预清零，特别是 IMG5 上下边框 |
| 图像会话左右 padding | 100 M 黑像素/秒，约 50 M 字/秒 | 25 M 黑像素/秒，约 12.5 M 字/秒 | 每行左右黑边 |
| BMP 窗口内像素 | 受 SD SPI 与像素缓冲可用量限制 | 不变 | 图片主体 |

写 FIFO 深度 512 字；上层发射块没有从该 FIFO 获得 `full` 回压，生成 FIFO 只在本地门控实际写入。SDRAM 还要与视频、音频读会话和刷新共享时钟与存储资源。连续零字把新路径推到与旧 SD 像素流完全不同的压力区间；限速给 FIFO 消耗、突发切换和读写仲裁留出时间。板上同一框架的 A/B 抓包在仅改零字发射节奏后出现可重复的大幅改善，因此“发射速率相关”是有板级 A/B 支撑的结论。

速率差可以直接从本工程计算。`sd_card_top` 高速分频参数为 0，100 MHz 系统时钟得到约 25 MHz SPI 时钟；传输一个字节至少 8 个 SPI 周期，即约 32 个系统周期。24-bit BMP 一个彩色像素需 3 字节，忽略扇区间隙也约需 96 个系统周期；两个彩色像素组成的写字通常比持续输出的黑字慢两个数量级。旧稳定版主要处理这种慢速像素流；新增填黑和每行 padding 则可以不等 SD 字节，迅速把 512 字 FIFO 与共享 SDRAM 读写仲裁推到另一种工作状态。单纯把数据从 0 换成别的颜色，不能替代控制发射速率。

**不能据此把某个 IP 内部寄存器定为唯一根因。** 官方 SDRAM 控制器是加密 IP；常规 Verilator 板级仿真使用 C++ 存储模型，不能复现器件上所有背压、刷新与时序行为。先前一批白字在静止画面重复 D 时逐字相同、重新装载后位置改变，说明故障随装载过程产生；但未在所有失败突发上同时取得可信的 `App_wr_en/addr/din` 与物理存储单元波形，无法再细分为写 FIFO、App 接口接受条件或 IP 内部执行。黑字全零不会让 SDRAM 时钟停止；该接口不是用数据翻转恢复时钟的串行链路。

## 后续调试准则与遗留项

1. **先固定 last known good，再 diff 新代码。** 用 `git log --oneline`、`git diff <稳定提交>..HEAD -- board_display/user_source/hdl_source` 列新增的 FSM、mux、计数、复位与跨域握手；不先归罪于时序报告里早已存在的违例。撤回被实测推翻的实验，例如填黑 ACK 等待和 128 字写突发。
2. **每次上板只变一个可检验因素。** 记录 bit/PLL 参数、SHA、生成时间、所用 BMP、缓冲区编号、音频是否配对、A/B 完整字数和 `seq` 缺口。旧 bit 与报告先备份；把 TD 综合、布局、布线分别计时，行数少不保证布线快。
3. **先确认探针确实覆盖待测会话。** A 的上下黑边是浏览器画布，不是填黑事务；B 是 SDRAM 返回的 3:1 抽样，不是 HDMI 后级逐像素全量。若复发，先分图像窗口、左右 padding、上下纯填黑三块统计，再决定把探针临时移到写 mux 后或 App 口。
4. **用局部仿真验证 RTL，板上验证硬 IP。** 真 FIFO 的 `SHOW_AHEAD`、使能/数据同拍、会话首末字与仲裁竞态须用针对性 TB；C++ SDRAM 模型无法验证加密控制器的物理接受条件。
5. **仍需单独跟踪的事项**：最终 IMG5 首抓出现一次 `0x08000000` 单字，重装后消失；当前 D 只抽 1/3 字；最终时序报告 Setup WNS 约 −5.699 ns、Hold WNS 约 −3 ns，最差 Setup 路径仍在 SDRAM DQ 采样，与功能修复是不同问题。`global_def.v` 的刷新周期宏仍沿用 125 MHz 数值而 PLL 当前为 100 MHz；本轮没有改它，未来调整须单独 A/B 综合和上板验证，避免破坏已验证的显示版本。
