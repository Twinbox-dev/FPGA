# 仓库清理与提交规则

本文区分正式产品构建、诊断构建和临时捕获，防止出现“板上测过的版本找不到源码或 bit”的情况。

## 可复现的板测版本

把一次板测称为“通过版本”，必须能从 Git 恢复以下内容：

1. 对应的 RTL 源码提交，以及该次构建使用的诊断覆盖源码或生成脚本。
2. 实际下载到每块板的 bit 文件。双板版本必须同时记录显示板和媒体板，不得只记录其中一块。
3. 板卡角色、JTAG cable 对应关系、测试步骤和实际结果。
4. 如果诊断构建禁用了 CV、音频或其他功能，必须在归档说明中列清楚；不得把它称为完整产品验收。

正式产品 bit 继续保存在对应 TD 工程的 `*_Runs/phy_1/` 中，并与产品 RTL、报告一同提交。确实用于板测且需要复现的诊断 bit，保存到 `boardtest/reference_builds/<用途_日期>/`；生成脚本和附加 RTL 放在 `boardtest/diagnostics/`。`boardtest/captures/` 只放可丢弃的临时输出、抓包和中间工程，不能作为唯一的源码或 bit 归档位置。

## 提交门槛

- 只有完成相应的仿真或板级验收后，提交说明才能称该功能“已验证”。未完成的构建标为候选或诊断，不冒充稳定版本。
- 通过验收的提交应同时包含对应源码、必要仿真、bit/报告和简短验收记录。仅文档提交不能被描述成新的功能或硬件版本。
- 每个提交聚焦一个可说明、可验证的阶段；提交消息简短，沿用“类别 - 内容”的格式。
- 默认只提交到用户指定的开发分支；不推送，不合并到 `main`，除非用户明确授权。
- 资源优化记录同时给出前后资源数和功能验收状态；资源减少不等于产品功能通过。

## 临时文件与日志

- `boardtest/captures/` 是忽略目录，只用于临时结果。若其中的构建被证明有复现或调试价值，先迁移必要的生成脚本、附加 RTL、bit 和说明到已跟踪目录，再清理临时输出。
- TD 的综合和布局布线报告以工程 `*_Runs/` 中已跟踪的报告为准；JTAG/CLI 的短期会话日志不留在仓库根目录。
- 根目录 `td_*.log` 与 TD 自动生成的 `.logw` 为临时会话日志，不作为板测版本记录；保留的验收证据写入归档说明或对应的工程报告。

## 当前多窗口诊断基线
