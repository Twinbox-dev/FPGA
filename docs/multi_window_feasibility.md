# 多窗口显示可行性评估

日期：2026-10-21
评估基线：`dual-V1` 显示板结构，仓库分支 `optimization/dual-board-architecture`

## 当前显示资源

本轮转场缓存候选之前的显示板布局布线报告为：13,178 LUT（67.23%）、9,825 FF（50.13%）、48 个 BRAM9K（75%）、3 个 BRAM32K（18.75%）、10 个 DSP（34.48%）、4 个 PLL（100%）。报告文件：

`board_display/td_project/lab_ex5_i2s_v1.0_Runs/phy_1/lab_ex5_i2s_v1.0_phy.area`

有两个图像帧缓冲区，每个 460,800 个 32-bit 地址字；另有两个各 587,776 字的音频区。转场使用 2,048×32-bit 的双行缓存。HDMI、以太网、SDRAM、GT911、字幕/OSD、音频频谱和转场仍都属于显示板产品路径。

### 转场缓存映射候选（2026-10-21）

`transition_line_buf.v` 的两个 1,024×32-bit 行缓存指定为 `bram_32k` 后，布局布线报告变为 13,175 LUT、40 个 BRAM9K、5 个 BRAM32K、10 个 DSP、4 个 PLL。相对候选前报告，LUT 减少 3，BRAM9K 回收 8 个，BRAM32K 增加 2 个。Setup WNS 保持 −5.699 ns，Hold WNS 从 −3.056 ns 变为 −3.054 ns。

`make transition-unit transitionpair` 通过，覆盖双 bank、100/75 MHz 跨时钟预取、行就绪、暂停回退、转场完成和帧像素路径。TD 综合、布局布线和 bitgen 均通过。生成 bit SHA-256：`1AAAB8D04348FC69357256159CD944C881A1B10036705436AFCFE6CF90777E95`。该 bit 已下载到显示板 cable0；`dual_board_cmd_probe.py --count 1` 的状态、音量设置 ACK、音量恢复 ACK 均通过，HDMI 可视效果留待用户确认。

## 两窗口

### 方案 A：同一图像复制到两个窗口

帧缓冲仍只读一次或由显示时序复用一份数据，两个视口绘制同一张图，可用于画中画、放大局部或不同尺寸的镜像预览。它不需要新增整帧缓存，新增资源主要是窗口坐标比较、缩放地址生成和少量像素复用控制。实现风险低，能先验证窗口合成及触控区域交互。

### 方案 B：两个窗口各自显示不同图片

当前两个图像缓冲恰好能承载两张静态图片，但会占满现有图像区，失去旧图/新图双缓冲。切图时需要选择以下策略之一：停用交叉转场并在窗口空闲时覆盖一张图；复用音频区前先迁移音频；或从 SD/媒体链路增加图像暂存区。不能同时保留双图独立显示、无撕裂替换和现有双图转场，除非增加外部 SDRAM 分区或另做更细粒度的窗口缓存。

两窗口若各渲染 640×360，像素总数仍是 1280×720 的一帧；因此按相同帧率与 RGB565 存储估算，顺序读吞吐大致不因窗口数量翻倍。真正的成本来自两套读地址生成、窗口/缩放逻辑、突发访问切换，以及两个图像源的缓存管理。

## 四宫格

四个 640×360 视口的输出像素总数同样等于一张 1280×720 全屏帧。若四格共享一个源图，可以复用帧缓存，主要增加独立缩放/地址控制；若四格显示四张不同图片，则要保留四份 RGB565 帧内容，理论需求约为现有两个图像区的两倍。按当前 460,800 个 32-bit 字/帧计，四帧需要 1,843,200 个 32-bit 字；当前两帧占用 921,600 字，短缺的两帧不能从显示板现有图像区直接获得。音频区目前正在承担双缓冲用途，不能直接当作空闲空间。

四路画面可采用逐行/逐块取数和短行缓存，而不必为每格都做完整帧缓冲；这会降低片上 BRAM 用量，但要求重新设计 SDRAM 仲裁与源端接口。本轮不实现这套 RTL，也不更改板间包格式。

## 建议路线

1. 先完成本分支已经规划的转场行缓存映射候选：将两份 1024×32-bit RAM 映射到 BRAM32K，确认回收 BRAM9K 数量、时序与转场仿真。
2. 新窗口功能先从“同源镜像/局部放大”开始，保持现有帧缓存和板间协议不变，评估窗口合成所需 LUT 与读吞吐。
3. 若目标是不同图片并排显示，先明确是否允许在多窗口模式停用淡入淡出，以及音频区是否可以在该模式下临时复用。未回答前，不改变 BUF0–BUF3 分区。
4. 四宫格不同图片建议作为独立架构阶段：先定义逐块缓存和 SDRAM 仲裁，再通过综合与显示板仿真核算，不直接增加四个完整帧缓冲。

## 约束和未验证项

- 当前基线的 4 个 PLL 已全部使用，新增窗口逻辑不得引入额外 PLL。
- 本文按 RGB565 每像素 16 bit、四个 32-bit 字打包两个像素估算帧容量；实施前应从显示读写地址生成器再次核对像素打包和有效容量。
- 本文是方案评估，不代表双窗口或四宫格 RTL 已实现或已经过板级验证。
