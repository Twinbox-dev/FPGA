# 板卡资源与时序基线

基线：`main` 的 `fc7c894`，TD 6.2、EG4S20BG256、100 MHz SDRAM 配置。
以下数字取自该提交的 `phy_1/lab_ex5_i2s_v1.0_phy.area` 与
`phy_1/final_timing.rpt`，是布线后报告，不是估算。用户试过把同一设计的
SDRAM PLL 改为 125 MHz，上板直接黑屏，已回退；后续拓展以 100 MHz
已验证 bit 为对照。历史 720p 早期报告的 7,443 LUT / 2 PLL 已不能代表当前工程。

## 资源

| 资源 | 使用 / 总量 | 占用 |
|---|---:|---:|
| LUT | 15,617 / 19,600 | 79.68% |
| 寄存器 | 10,008 / 19,600 | 51.06% |
| BRAM 9k | 38 / 64 | 59.38% |
| DSP | 5 / 29 | 17.24% |
| PLL | 4 / 4 | 100% |

LUT 尚有 3,983 个，但没有充足的无条件扩展余量；PLL 已用满，
新增独立时钟源首先受此约束。报告的层次统计使用 `lut`、`ripple` 等不同列，
不要把某个子模块的 `lut` 列直接与全芯片 `#lut` 相加比较。

本次 TD 日志记录门级综合约 2m33s，布局 1m57s、布线 3m52s
（布局+布线合计 5m49s）。因此迭代等待不只是 RTL 综合阶段；
“LUT 高占用导致过度优化”尚无直接证据。优化前后应分别记录这三个阶段，
避免把工具运行波动误判为源码效果。

较大的顶层区域是 `sd_card_bmp`（约 6,539 LE、其内 `fat32_ro` 约
2,143 LE）和 `eth_subsys`（约 5,408 LE、其内 UDP/IP 协议栈约
3,246 LE）。这只是优化候选的定位；状态机行数和实例面积都不能单独
证明逻辑冗余。写侧/读侧调试流也是 PC 预览功能的一部分，不能当作
“临时代码”直接删除。应逐模块改动、逐次比较门级/布线面积、时序和功能。

## 时序与行为边界

当前报告：全局 SWNS −5.699 ns、STNS −1565.496 ns；`ext_mem_clk`
为 100 MHz，报告该组 SWNS −5.699 ns；`sd_card_clk` 为 100 MHz，
该组 SWNS −3.407 ns；`video_clk` 为 75.002 MHz，该组 SWNS
−3.963 ns。**上板功能正常不等于静态时序收敛。** 历史报告含厂商 SDRAM
IP 与跨域路径，必须按起点、终点和约束逐条判读，不把负数直接归因于新功能。
详细排查方法见 [`timing_report_howto.md`](timing_report_howto.md)。

需要单独审查的遗留点：`include/global_def.v` 中
`SDR_CLK_PERIOD = 1000000000/125000000` 仍按 125 MHz 计算，而
当前 SDRAM PLL 输出是 100 MHz；该宏参与加密 SDRAM 控制器的
`SELF_REFRESH_INTERVAL`。这是**代码/配置不一致的事实**，但尚未做
100 MHz 宏值的受控板级 A/B，不能在“纯清理”里悄悄改掉。

## 存储分配

SDRAM 用户地址共 2,097,152 个 32 位字，当前分成两块视频缓冲
`460,800 × 2` 和两块音频缓冲 `587,776 × 2`，恰好用满。
新增帧缓冲需要重新规划这四块空间；缩短音频缓存是候选方案，但要同时
验证配对 WAV、切图和欠载行为，不能仅改地址常量。

## 优化验证顺序

1. 先保存本报告和综合耗时作为对照，确定热点模块以及必须保留的功能。
2. 每次只改一个模块；先运行相关定向仿真，再跑七卡回归。
3. 用同一 TD 版本、约束、PLL 设置比较 LUT、BRAM、时序及综合耗时。
4. 只有功能/资源/时序均可接受，才交由上板确认并合入稳定分支。
