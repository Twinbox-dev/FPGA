# 板级调试面板与音频噪声定位（2026-09-27）

> **状态（2026-09-29）：七段调试面板已退休。** UART 状态包（`docs/uart_link.md`，
> `'S'` 回读）已是同一组遥测的唯一出口，面板在 top 里只显示固定 `'8'` 占位，
> `seg_scan/seg_decoder` 与引脚约束保留给后续模块复用。
> 本文保留为历史方法论与判读经验（面板读数在第五/六轮的定位价值是真实的），
> 但未来的上板观测请用 `S` 回读状态包；"每轮上板前先问这轮能读出什么"的
> 原则不变，只是观测载体从 6 位数码管换成了 UART 包。

## 方法论：数码管调试面板（上板观测的标配）

板上 6 位数码管原本只用 1 位。前四轮上板每轮只换来 1 bit 信息，全靠猜——
这是"挣扎太久"的根源。第五轮起把全部 6 位接成只读调试面板
（`top_tf_hdmi_audio.v`，不影响功能），**一次综合回答所有悬而未决的问题**。

面板布局（`seg_data_5..1`，物理位置以"显示状态码的那位"为锚）：

| 位 | 内容 |
|---|---|
| d5 | state_code（1 空闲 2 挂载/扫描 3 FIFO 握手 4 写帧） |
| d4,d3 | fat32_ro FSM 状态（hex 两位：08=MOUNTED 空闲，02=扇区流中，09=ERR…） |
| d2 | flagA = {video_pll_lock, sys_pll_lock, Sdr_init_done(SDRAM), display_valid} |
| d1 | flagB = {hdmi_locked, fat_err, disp_buf_idx[1:0]} |

判读（健康读数 `1|08|F|8`，disp_buf 翻转时 flagB 8↔9）：
- flagA=F → 两个 PLL + SDRAM init + display_valid 全好
- flagA<8 → PLL 问题（解释无信号）；bit1=0 → SDRAM init 挂（解释无信号）
- flagB bit2=1（C/D）→ fat32 进 S_ERR = 扇区数据坏（重插卡）
- fat 状态 01/02 卡死 → 扇区读握手挂（sd_adapter 层）
- **本次实战**：读数 `9F801/8F201/8F204` 全健康 + flagB 8↔9 翻转 = 切图提交
  的直接证据；"图像全无"实为 TF 卡接触不良。

教训：**每次上板前先问"这轮能读出什么"**。观测位不够就先扩面板再综合。

## 音频噪声根因（两个，都藏在主仿真盲区）

主仿真（boardtest）的 frame_read_write 是 C++ 模型——**真实读/写引擎 RTL
从未被仿真过**。板级"滋滋噪声"（二、三、四、五轮皆有）实为两个叠加的 bug：

### 根因 #4：写引擎垂直翻转误伤音频（frame_fifo_write.v）

`WRITE_V_FLIP`（取消 BMP 自下而上存储的 640×480 行翻转）原本对全部写通道
生效——音频字（index 2/3）被按行块倒排地址打散写进 BUF2/3，播放顺序读 =
读未写区域 = 噪声。特征全对上：**静音 WAV 打乱仍静音（TST0 无声✓）、
正弦打乱=滋滋噪声✓、切图换一种排列=爆音"一声拉高"✓**。
修复：`vflip_en = WRITE_V_FLIP && (write_addr_index_d1[1]==0)`，仅图像翻转。

### 根因 #5：读引擎音频会话被视频抢占后永不恢复（frame_fifo_read.v）

音频整段读被 512 字 FIFO 节流拉长到秒级，视频按帧（16.7ms）在突发边界抢占；
抢占时音频的地址/计数/长度被视频会话覆写、且音频请求早已撤（ack 即撤），
会话死亡 → 每段只放 ~30ms 后永久静音。修复：抢占时快照
`aud_{addr,cnt,len}_hold`，视频帧读完（S_END）且无新音频请求时自动续读
（FIFO 不清，消费侧无感知）；有新请求（PL 换缓冲）则走全新会话。

### 根因 #6：播放域 rd_en 是 4 拍宽脉冲，真实 FIFO 每拍弹一字（sd_card_bmp.v）

现象：音调/静音判断全对（相对音高不变），但 5s 文件 ~1.26s 就回卷一次咔声、
click 波形被 4 抽 1 打碎。账：播放消费被 tick48 锁死 6000 字/s，5s=30208 字
必须 5s 一圈 → 实测 <1.3s 圈 = FIFO 在丢 3/4 数据。真凶：`rd_en_r` 的清零
写在 `if(en25)` 里 → rd_en 置位后保持 4 个 clk，而 rfifo_32_32_512 的语义是
**re 为高的每一拍弹一字**（IP 文件 `IP/afifo_32_16_256.v`，settings.cfg 显示
该模块即由它生成）→ 一次"读"弹 4 字只捕获 1 字：FIFO 净消耗 ×4（24000 字/s
→ 1.26s 圈）+ 音调 ×4（1k 实为 4k、500 实为 2k，相对关系不变故听不出）。
修复：`rd_en_r <= 1'b0` 移出 en25 门控（每拍清零，en25 内置位同拍后写覆盖）。
**最毒的一环**：boardtest C++ 模型注释自认"rd_en 为 en25 域 4 拍宽脉冲：按
上升沿计一次取字"——建模时发现了 4 拍宽脉冲，却按边沿触发建模，把 bug 当
正确行为写进了模型。教训：**模型发现与假设不符的接口行为时，去查真实器件，
不是把假设写成模型。**

### 为什么仿真没抓到 & 怎么补的

C++ 写模型按到达顺序 append（无地址概念）→ 根因 #4 不可见；
C++ 读模型没有视频抢占概念 → 根因 #5 不可见。
补：`make -C boardtest readeng` —— 用真实 frame_fifo_read/write RTL +
行为级 FIFO + SDRAM 桩的自检测试台（`vsrc/tb_readeng.v`）：
T1 音频顺序写 / T2 图像翻转保留 / T3 音频会话扛住视频反复抢占 / T4 重发新会话。
**教训：主仿真替代了哪个模块，哪就是盲区；被替模块一改动，必须补 RTL 级用例。**

## 板上验证结论（2026-09-27 第五/六轮）

#4（写翻转误伤音频）/#5（会话被抢占致死）/#6（rd_en 4 拍宽→消耗 ×4）三修
上板全部验证通过：音调/时长/静音/切图/自动轮播全对。残余小瑕疵：静音 WAV
在 5s 回卷点有一次小爆破（疑为回卷重启时 aud_valid gap 或 FIFO 清空后首字
旧值被捕获，见 TODO.md）。

## 面板读数实战价值复盘

两轮上板判读全部靠面板完成：flagA=F 锁定"系统健康、问题在音频数据通路"；
flagB 8↔9 翻转证明切图提交在工作；"图像全无"一轮靠面板排除了系统性故障、
